# Security Design Review — `harden-dev-scripts-and-networking`

> Generated by **GLM** (glm-5.2) via `/code-review` at medium effort, then
> independently re-verified against the tree and live Docker/Node behavior.
> Scope: `git diff main...HEAD` plus working-tree state. 8 finder angles
> (line-by-line, removed-behavior, cross-file tracer, security-design,
> simplification, efficiency, altitude; conventions returned nothing — no
> CLAUDE.md governs this repo), 1-vote verify. Verification status per finding
> is recorded in [Veracity audit](#veracity-audit).

## Summary

This branch hardens a Node 24 + TypeScript Docker template against npm
supply-chain worms (malicious `postinstall` credential harvest + require-time
exfil). The threat model and decisions are documented in HARDENING.md. The
hardening is thoughtful, but several controls are bypassable, mis-ordered, or
shipped as comments-only rather than live config. Findings below are ranked
most-severe first.

## Findings

### 1. Base-image digest is split-brained across dev and prod (supply-chain)

**`dev/_lib.sh:24`** — `IMAGE="$(sed -n 's/^NODE_IMAGE=//p' "$PIN_FILE" | head -n1)"`
takes the **first** `NODE_IMAGE=` line from `.env`. `docker compose` interpolates
the **last** duplicate key (verified empirically: a two-line `.env` resolves to
`SECOND` under `docker compose config`). A `.env` with two `NODE_IMAGE=` lines
silently runs dev scripts against one digest and prod against the other — dev
tests pass on the known-good image while prod ships the other, with no warning.
The digest pin is the template's headline supply-chain control.

Note: the only in-repo writer of that line, `dev/bump-node`, uses
`sed 's|^NODE_IMAGE=.*|...|'` with no address — it rewrites *every* matching
line, so it cannot itself create the duplicate. The trigger is a manual edit or
an external tool. The parsing asymmetry is real either way, and the fix is cheap.

**Fix:** error when `NODE_IMAGE` count ≠ 1 instead of `head -n1`, so a second
line fails loudly in both dev and compose.

### 2. The network-off security floor is bypassable and lies in its status output

**`dev/_lib.sh:76`** (`parse_net_args`) + **`dev/test:13-14`** / **`dev/shell:19-20`** —
`parse_net_args` consumes only the exact token `--net`. `--net=host`,
`--network`, and `--network=host` all fall through into `pass_args`, which are
emitted **after** `--network none`. Docker's last-flag-wins gives the container
host networking — while the posture banner, set once at parse time, still prints
`network: OFF`.

`./dev/test --network=host` defeats exactly the require-time-exfil threat the
OFF-by-default floor exists for (HARDENING §9): the bypass is trivial, and the
safety signal is wrong.

**Fix:** match `--net` / `--net=*` / `--network` / `--network=*` and reject or
consume them (and the following token for the space-separated forms). Re-derive
`net_posture` after parsing so the banner reflects the real state.

### 3. dev/run binds the secrets-holding dev process to 0.0.0.0

**`dev/run:34`** — `-p "${HOST_PORT:-3000}:3000"` has no IP prefix, so docker
binds `0.0.0.0`. `dev/run` also loads `--env-file "$ENV_FILE"` (tokens from
`~/.config/<project>/env`) into the process. On shared WiFi (coffee shop, office
LAN) a peer can `curl <host-ip>:3000` and reach that process. Today the app only
serves `${greeting}`, but any future route bug or require-time payload in a dep
hands the in-process secrets to a remote attacker without ever compromising the
host.

**Fix:** `-p 127.0.0.1:${HOST_PORT:-3000}:3000`.

### 4. Shipped prod config is LAN-exposed and egress control is comments-only

**`docker-compose.yml:22`** — `ports: - "${HOST_PORT:-3000}:3000"` → `0.0.0.0` in
prod with `env_file` secrets loaded. **`docker-compose.yml:34-52, 79-85`** — the
entire egress-control design (proxy sidecar, `internal`/`ingress` network split,
masquerade-off trick) is **commented out**. HARDENING §2 (egress allowlist) and
§6 (network isolation) are unshipped prose, not live controls.

Even if an operator uncomments the proxy sidecar, the app's
`networks: [internal, ingress]` line stays commented, so the app keeps direct
egress and the tinyproxy allowlist is bypassed entirely. The §2/§6 claims are
comments only.

**Fix:** prefix `127.0.0.1:` in `ports`, and either implement + test the network
split or drop the egress-control claim from HARDENING.md.

### 5. Proxy config (when enabled) is an open relay with an unverified filter

**`proxy/tinyproxy.conf:7`** — `Listen 0.0.0.0` + `Allow 0.0.0.0/0` makes
tinyproxy an open relay on its network. The sidecar service is commented out in
compose today, but the `proxy/filter` file was actively edited in this diff and
HARDENING §2 cites it as the egress control — so this is pre-implementation
design debt, not a live exposure.

When enabled, any container or host on the proxy's network can relay to
allowlisted domains (Discord-webhook spam, billed Anthropic API calls attributed
to this host). The second concern — a filter bypass via
`http://discord.com@evil.com/exfil` (host `evil.com`, URL string containing
`discord.com`) — is **unverified**: `FilterType fnmatch`'s match target (URL
string vs parsed host) varies by tinyproxy version, and the repo's own
`proxy/filter` header asserts it matches "the FULL hostname," which would deny
that bypass. Needs an actual tinyproxy test before being treated as a confirmed
hole.

**Fix:** restrict `Allow` to the app alias only; add denial tests for
`discord.com@evil.com`, `discord.com.evil.com`, and CONNECT-form `evil.com:443`.

### 6. dev/run forwards pass-through args without parse_net_args

**`dev/run:36`** — `dev/run` passes `"$@"` straight to docker run without calling
`parse_net_args`. `./dev/run --net` (carried over from `dev/shell` muscle memory)
makes docker treat `--net` as the `--network` alias and consume the following
token (`-e`, `PORT=3000`, or the image ref) as its value, producing a confusing
"unknown network" / missing-image error instead of a clean start.

`parse_net_args` was built specifically to prevent this (its comment says an
unconsumed `--net` "swallows the next arg (the image ref) as its value"), but
the one script that forwards the most pass-through args doesn't use it.

**Fix:** `dev/run` should call `parse_net_args` (or reject `--net`/`--network`
outright, since run is network-on).

### 7. resolvePort test depends on the host env

**`src/index.test.ts:16`** — the "resolvePort defaults to 3000 when PORT is
unset" test calls `resolvePort(undefined)`, which triggers the default param
`raw = process.env.PORT`, but never `delete`s `process.env.PORT`. The sibling
greeting test does `delete process.env.GREETING` for the same guarantee. If
`PORT` is exported in the environment (CI, a shell with `export PORT=8080`),
`resolvePort(undefined)` returns 8080 and `assert.equal(..., 3000)` fails — or
masks a real fallback regression when `PORT` happens to be 3000. Confirmed by
running the suite with `PORT=8080`: the test fails.

**Fix:** `delete process.env.PORT` at the top of the test.

### 8. ensure_cache_volume spins a container on every dev invocation

**`dev/_lib.sh:62`** — `ensure_cache_volume` runs `docker run --rm -u root ...`
(full container create+start+remove, ~0.3–2s of daemon round-trips + image-layer
plumbing) on every `dev/install`, `dev/update`, and `dev/shell` call. The
in-container `stat` only short-circuits the `chown`, not the expensive part —
the container start. Ownership persists on the named volume, so after the first
run this is a no-op that still pays full container-start cost.

**Fix:** check volume existence/ownership via `docker volume inspect` before
spinning a container.

## Addendum — late-arriving line-by-line findings (not in the capped 8)

These surfaced from the line-by-line finder after the formal 8 were reported;
they are real and worth acting on.

- **`src/index.ts:32` — SIGTERM handler has no shutdown timeout.** `server.close()`
  waits for all existing connections, including idle HTTP/1.1 keep-alive sockets,
  to close naturally. A client holding an open keep-alive (or a long-poll) blocks
  the callback until compose's `stop_grace_period` (default 10s) expires and
  SIGKILLs the process — dropping in-flight responses anyway, defeating the
  "finish in-flight responses and go" goal. Use `server.closeIdleConnections()`
  (Node 18+) or a `setTimeout` + `closeAllConnections()` to bound the wait.

- **`dev/update:52` — `|| die` misdiagnoses every failure as the 7-day cooldown.**
  The EXIT trap restores the lockfile on any non-zero exit, but the `die` message
  always tells the user "a dep pinned to a version published in the last 7 days
  cannot satisfy the cooldown; retry once it ages past 7 days." A transient
  registry/network error, disk-full, or malformed `package.json` sends the user
  on a 7-day wait for a 30-second blip.

- **`dev/run:15` — env-file validation diverges from docker run and compose in two
  more ways.** It rejects *indented* `KEY=value` lines (leading whitespace) that
  `docker run --env-file` actually accepts, blocking `./dev/run` on a valid file.
  And it doesn't catch inline `#` comments: `API_KEY=secret # prod` becomes
  `secret` under compose but `secret # prod` under `docker run --env-file` — the
  same file meaning different things, exactly what the validation comment claims
  to prevent. Both confirmed by running both parsers on the same file.

- **`src/index.ts:7` — `resolvePort` accepts hex/scientific notation.** `Number("0x10")`→16,
  `"1e3"`→1000, `"0o17"`→15 all pass `Number.isInteger` and the range check, so
  `PORT=0x50` silently binds port 80 (privileged) instead of failing fast. Low
  severity — contradicts the "garbage must fail loudly" comment.

## Veracity audit

Independent re-verification against the tree and live Docker/Node behavior.

- **F1 — mechanism confirmed, trigger narrowed.** Compose resolves a duplicate
  `NODE_IMAGE=` to the **last** value; `_lib.sh` takes the **first**. But
  `dev/bump-node` rewrites every matching line, so it cannot produce the
  duplicate — the trigger is a manual edit or external tool. Reframed above.
- **F2 — confirmed.** `parse_net_args` matches only the exact token `--net`
  (`dev/_lib.sh:76`); other forms fall into `pass_args`, emitted after
  `--network none`. Last-flag-wins + stale banner both hold.
- **F3 — confirmed.** `dev/run:34` has no IP prefix; `--env-file` loaded.
- **F4 — confirmed.** `docker-compose.yml:22` binds `0.0.0.0`; egress design
  (lines 34-52, 79-85) and the app's `networks:` line (42) are all commented.
- **F5 — split.** Open relay (`Allow 0.0.0.0/0`, `Listen 0.0.0.0`) and
  sidecar-commented are confirmed. The `discord.com@evil.com` filter bypass is
  unverified and partly contradicted by the `proxy/filter` header; flagged as
  such above.
- **F6 — confirmed.** `dev/run` never calls `parse_net_args`; `--net` would
  consume the following token.
- **F7 — confirmed empirically.** Suite run with `PORT=8080` exported:
  `✖ resolvePort defaults to 3000 when PORT is unset`.
- **F8 — confirmed, callers corrected.** `ensure_cache_volume` runs a container
  per invocation; `stat` only gates the `chown`. Callers are `dev/install`,
  `dev/update`, and `dev/shell` (verified via `grep -rn ensure_cache_volume dev/`)
  — `dev/test` does not call it, contrary to the original finding text.
- **A1 — confirmed.** `src/index.ts:32` calls `server.close()` with no idle
  timeout / `closeAllConnections`.
- **A2 — confirmed.** `dev/update:52` `die` message is fixed to the 7-day
  cooldown regardless of failure cause.
- **A3 — confirmed empirically.** `docker run --env-file` accepts an indented
  `KEY=value` (returns `indented_value`) that `dev/run` rejects; inline `#`
  resolves to `secret # prod` under `docker run` vs `secret` under compose.
- **A4 — confirmed empirically.** `Number("0x50")`→80, `Number("1e3")`→1000,
  `Number("0o17")`→15 all pass the integer + range checks.
- **Project-name sanitization divergence — refuted, correctly.** In a `node.orb`
  directory, `docker compose config` yields project name `nodeorb`; `_lib.sh`'s
  sanitization also yields `nodeorb`. The `ENV_FILE` path and compose's
  `${COMPOSE_PROJECT_NAME}/env` resolve to the same file. (Dropped from the
  findings as a non-issue.)

## Altitude note (not a bug)

PORT is now pinned in three places — `docker-compose.yml` `environment`,
`dev/run -e PORT=3000`, and `src/index.ts`'s default — with no declared source of
truth. Moving the app to `:4000` means editing all of them; miss one and it
breaks silently (e.g. change the mapping to `4000:4000` but leave
`environment: PORT: "3000"` → app listens on 3000, mapping targets 4000,
connections refused with no error logged). Worth a single constant or a comment
naming the authority.
